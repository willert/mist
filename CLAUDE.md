# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`App::Mist` (the CLI is `mist`) is the upstream source of the **mist** Perl environment manager that the user's global `~/.claude/CLAUDE.md` describes as the homebrew Carton/local::lib wrapper used across WeCARE/SiG projects. This repo *implements* `mist`; downstream projects (`teledoit`, `sig-cms`, …) merely *use* it via a generated `mpan-install` script.

Two things make this codebase unusual:

1. **mist bootstraps itself with itself.** The repo ships its own `./mpan-install` (a fatpacked installer generated by `mist compile`) and its own `./mpan-dist/` package mirror. Running `./mpan-install` builds `./perl5/` for the project, exactly like in any downstream project. The wheel-of-cheese problem (you need mist to build mist) is solved by `extlib/` containing the minimum bootstrap of `local::lib`, and by the `rebuild-5.20.3.sh` / `docs/bootstrap.sh` scripts for when the existing `mpan-install` itself is broken.
2. **`mpan-install` is a build artifact, but it is committed to git.** Downstream projects vendor it. Regenerate it with `mist compile` after any change to fatpacked code (anything pulled in by `lib/App/Mist/Command/compile.pm` — see "Architecture" below).

## Common commands

All commands assume `./perl5/` already exists (i.e. someone has run `./mpan-install` at least once for the current Perl version). Run from the project root.

- **Bootstrap / rebuild local Perl env:** `./mpan-install` (or `./mpan-install --perlbrew 5.20.3` to pin Perl). Reads `cpanfile` + `mistfile`, installs into `./perl5/perl-<ver>-<arch>/`.
- **Run a script under this project's env:** `./mist-run <cmd…>` (symlink to `perl5/bin/mist-run`).
- **Tests:** `./mist-run prove -Ilib t/` - a sizeable suite (40+ files, 1000+ tests). Most files need the project env, so run the full suite under `./mist-run`; the end-to-end installer tests (`t/mpan-install-activation.t` and friends) additionally need `mist` on PATH and this repo's built 5.20.3 env, and skip when either is missing.
- **Single test:** `./mist-run prove -Ilib -v t/mistfile.t`. Core-only files (`t/generation.t`, `t/mpan-install-activation.t`) also run under a bare `prove -Ilib`.
- **Regenerate `mpan-install`** after changing any of the modules fatpacked into it: `mist compile`.
- **Rebuild the *bundled* `mpan-dist/` from scratch** (rarely needed — only when fatpacked deps in the installer itself break): see `docs/bootstrap.sh` and `rebuild-5.20.3.sh`.
- **Re-index `mpan-dist/`** after manually dropping a tarball in: `mist index`.
- **Read-only inspection of the resolved mistfile:** `mist lib_paths` prints the library paths the env would use.

There is no separate lint step. Build/release is via Minilla (`minil`), but releases are gated — `minil.toml` has `do_not_upload_to_cpan = true`.

## High-level architecture

### Two halves: build-master vs. host

`docs/workflow.txt` captures the original mental model and is still accurate:

- **Build-master side** (this repo, or any project using mist): commands like `mist compile`, `mist index`, `mist inject`, `mist merge`, `mist upgrade`. These curate `mpan-dist/` (a CPAN-shaped mirror of pinned tarballs) and regenerate `mpan-install` from it.
- **Host side** (the generated `mpan-install` script): a single fatpacked Perl script that, on a target machine, sets up perlbrew, picks the right Perl, and runs `cpanm` against the embedded `mpan-dist/` mirror to populate `./perl5/`. The host never needs `mist` itself, just Perl + a C toolchain.

`mpan-install` is built by **`lib/App/Mist/Command/compile.pm`**. Read that file first if you want to understand what ends up in the installer — it literally concatenates module source for `Getopt::Long`, the cpanminus fatscript, `Devel::Check{Bin,Lib,Compiler}`, `Probe::Perl`, `Mist::Distribution`, `Mist::Environment`, the project's parsed mistfile rendered via `as_code`, `share/cmd-wrapper.bash`, then the three `Mist::Script::*` modules (`perlbrew`, `install`, `usage`) which are the actual logic that runs on the host.

### The mistfile DSL

`mistfile` is a Perl DSL (not data) parsed by **`Mist::Environment`** in a fresh package with the verbs `perl`, `assert`, `prepend`, `notest`, `ccflags`, `merge`, `script`, `dist_path` injected via `_bind`. Each verb is a method on **`Mist::Distribution`** (the immutable parse result). `Mist::Environment::as_code` is what `compile` uses to embed the parsed mistfile into `mpan-install` — note the package name is overridden to `DISTRIBUTION` there so the host script can find it.

`merge { … }` blocks share a global `$Mist::Distribution::merging_dist` while their body runs; `store_dist_info` checks that variable to route entries into the merged sub-dist as well as the parent. This is how dependency sets from sibling projects get folded together (e.g. the `mistfile` here is small precisely because downstream projects' mistfiles merge each other).

### The CLI shape

`App::Mist` is a stock `App::Cmd` app. Each subcommand is a file under `lib/App/Mist/Command/`, and `App::Mist::Context` is the shared object (lazy-built, accessed via `$self->app->ctx`) that holds: `project_root` (found by walking up for `mistfile`/`cpanfile`), `mpan_dist`, `local_lib`, the parsed `Mist::Distribution`, the cpanm path, and perlbrew root. `App::Mist`'s `BEGIN` block is doing real work: it bootstraps `local::lib` from `extlib/` if needed and then re-imports `local::lib` pointing at `./perl5/perl-<ver>-<arch>/` so that the mist CLI itself runs under the project-local Perl. Touch that block carefully.

`Context::ensure_correct_perlbrew_context` is the other tricky piece: if `$ENV{PERLBREW_PERL}` doesn't match the project's requested Perl, it re-execs the current command under `perlbrew exec --with <ver>` via `share/perlbrew-wrapper.bash`. So a single `mist` invocation can fork-and-exec itself once before doing real work.

### Minilla integration

`lib/Minilla/` and `lib/Mist/Minilla/` are *not* mist itself — they are Minilla plugins/overrides used when mist-managed projects also use Minilla for releases. `App::Mist::Command::prerelease` and `release` shell out into this. Unrelated to the install path; ignore unless working on release tooling.

## Conventions and gotchas

- **`perl5/` and `mpan-dist/` in this repo are real, not artifacts to ignore.** `perl5/` is the local env for *this* project (gitignored); `mpan-dist/` is the bundled CPAN mirror that gets fatpacked into `mpan-install` (committed).
- **Perl version is pinned to 5.20.3** in `mistfile`. Newer Perls *can* be used by passing `--perlbrew` to `mpan-install`, but the bundled tarballs in `mpan-dist/` were curated for 5.20.3 — expect breakage on much newer Perls (the recent `cpanm` update in `b06e58f` exists specifically to make the installer work on 5.38+).
- **Don't `cd` into `perl5/`** to "fix" things — wipe it and re-run `./mpan-install` instead.
- **`--system-perl` is host-side; `--force-system-perl` is the CLI's escape, and they are not the same thing.** `./mpan-install --system-perl` is a blessed mode: a deploy host or container legitimately builds against its own perl, and the choice is recorded in `perl5/.mist-system-perl`. The CLI does *not* inherit that blessing. Build-master commands re-exec under the pinned perl so that what they produce is reproducible, and `Context::ensure_correct_perlbrew_context` demanding perlbrew is that working as intended. What the CLI grants is a per-invocation escape, `mist --force-system-perl <command>`, for a host that cannot supply a perlbrew context: it must be typed every time, cannot be set from the environment, warns on use, and is **refused for `compile`, `build_dist`, `release` and `prerelease`** - those emit artifacts other checkouts and other people consume, and nothing in the result records which perl resolved it. The CLI reads the marker only to make the no-perlbrew error name the escape; it never decides behaviour from it, which is what keeps the two halves from growing separate definitions of what `--system-perl` means. (Earlier guidance here said teaching the CLI about the marker was out of scope by design. The kernel of that was right - artifact production must not escape the pin - but it was stated as "the whole CLI is out of scope on such a host", which vendoring a sibling on a perlbrew-less box disproves.) The installer needs no local::lib on the host either: it rides in fatpacked via the cpanm fatscript, and the generated rc bakes local::lib's *output* at install time.
- **`mpan-install`'s version stamp lags, and that is not drift.** Its second line, `# Generated by App::Mist version <X>`, records the mist that last ran `mist compile` - not this repo's version, and not the release it ships in. A release bumps `lib/App/Mist.pm` without recompiling, so the stamp stays at whatever version last compiled, frequently several releases back. Read the repo's version from `lib/App/Mist.pm`; the stamp answers "which mist generated this installer", a question worth asking of a *downstream* project's copy, not of this one. Regenerate when fatpacked code changes, never to make the stamp match a release.
- **Shebangs:** `mist compile` walks the project (respecting `MANIFEST.SKIP`) and warns on `#!/usr/bin/perl` or `#!/usr/bin/env perl5.*` style shebangs. Use `#!/usr/bin/env perl`.
- **Commit when confident, push only on explicit ok** per the user's global CLAUDE.md. Releases happen through Minilla; never hand-bump `Changes` or version numbers without asking.
- **Keep the `mist` skill in sync; it lives elsewhere.** mist's user-facing handbook is the `mist` skill, canonical at `~/Devel/claude-devtools/claude/skills/mist/SKILL.md` and loaded across teledoit, sig-cms and the other WeCARE/SiG projects. It versions in claude-devtools, separate from this repo, so it can drift silently from mist's behaviour. When a change here alters user-facing behaviour (a command or flag, the CPAN-dependency or release workflow, mistfile/`assert` or `mist-run` semantics), check whether the skill needs the same edit. If the skill is accessible in your session, update it there as its own claude-devtools commit; if it is not, flag that it likely needs updating so the change is not lost.
